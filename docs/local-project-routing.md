# Local project routes and workspace runtime

Implemented checkpoint, 2026-10-02 (Asia/Singapore). This is part of the ongoing [project-system implementation](current/project-system-implementation.md). Sidebar discovery, creation/import and default project settings now use local identities; shared promotion and full native acceptance remain separate work.

## Resolution and presentation

`resolveLocalProjectRoute` reads the durable catalog snapshot. Exact local identity wins, followed by an existing cloud association, then a unique local slug. Hidden entries can be opened by an explicit link. Removed entries supply no execution owner. An ambiguous slug supplies choices rather than silently selecting a folder; the chooser shows recorded local paths when available.

New `lpj_` route keys never enter legacy cloud discovery. Historical route keys can still resolve an existing native binding while metadata loads. Unknown legacy/shared links wait for catalog discovery and verified cloud readiness, then use `projects.getAccessibleByRouteKey`. That endpoint authenticates the caller before normalizing the untrusted route string with Convex and checking access. It rejects the local namespace. Unknown shared discovery does not yet create a local catalog entry; that belongs to the explicit shared-association workflow.

`useProjectRouteData` and `useAccessibleProject` expose the local entry/identity separately from a genuine optional `Doc<projects>` and cloud association. Local presentation supplies the title and folder slug. A local-only route creates no cloud watches even with a configured, authenticated client. Known associations query their genuine ID, including when entering through a local slug. Cached documents must match the association or legacy locator; a cache cannot associate an unknown local route with another cloud project. Cached presentation never authorizes remote access.

A fresh authenticated response can refresh the existing association's shared name/status/device scope through local IPC. A cached response or navigation hint cannot create an association. Local aliases, visibility, folder slug and workspace bindings are preserved.

Cloud-ID and local-slug links to an existing local entry canonicalize to its local route. URL suffixes, query/hash, tile intents and history state survive. Matching navigation hints have their project locator updated; unrelated hints remain untrusted. Header changes navigation, sidebar selection, workbench scopes, lane/cache ownership and runtime keys use the local identity.

## Runtime and local changes

`WorkspaceRuntimeConfig.projectId` is the device-local execution owner. Its separate optional `cloudProjectId` is used only at shared boundaries. Local runtime providers and host policy require a project/workspace binding, without requiring a cloud principal. Focused work and critical headless terminals/Dev Servers remain hosted. Updating cloud metadata changes runtime configuration without replacing the runtime key or retained session/PTY snapshot.

Project-switch prefetch takes an explicit optional genuine cloud ID. Local workspace/lane/Git prefetch continues independently; no cloud ID is fabricated from its local project key. The changes header and Changes page can display native Git diffs without a cloud project document. Shared change history waits for cloud readiness and reports unavailable state without blocking local diffs.

Create/import opens the returned local project with a workspace-qualified one-shot intent. The visible matching project/workspace consumes it only after its scope is ready; a retained previous surface must leave it untouched. Ordinary creation/import uses `ensureTile` to focus an existing assistant or create one if absent, so repeated folder opening and renderer reload preserve the same tile. Explicit Add Tile actions retain their usual new-tile behavior. Its lane lives in route state rather than a duplicate URL query that could clear the intent during cleanup. A non-Git folder is ready when the concrete workspace and catalog lane agree on project/workspace ownership and both have a null Git root. Missing, stale or unknown catalog data remains pending, and Git workspaces still wait for their branch identity.

An assistant binds to the local workspace root through the local T3 server. After `project.create` acknowledges, the renderer refreshes the committed orchestration snapshot before deciding whether that project exists. This avoids a false binding error when the command reply precedes the pushed read model. The workspace lock serializes binding across tiles/renders; a cancelled settings/render effect leaves its replacement able to reconcile the project, and cannot reset the replacement's binding status. These operations create no cloud project association and do not start a provider conversation.

After a journal-backed original-folder repair, the workbench first confirms the full repair chain from its saved binding revision. It preserves tile identities, selection and the layout reset key, flushes the layout with the new binding revision, and blocks stale outgoing layout writes. Unconfirmed catalog reads leave the old state intact for retry; a genuine unproven binding replacement still resets private tiles. The assistant binding lock then checks completed catalog evidence before rebasing an existing T3 project's root. Every intervening revision must be completed if a chat was absent during several moves. Running chats block reconciliation; idle native provider sessions stop before metadata changes, and the authoritative snapshot must confirm the new root and stopped sessions. Existing native project/thread IDs, workbench tiles, history and draft attachments survive. Draft/history roots change only for the exact old project/workspace/root association; independent thread worktrees remain untouched. Losing the metadata reply does not create another assistant project. Local settings and their recovery controls remain available when a workbench binding is broken.

Local checkpoint refs are cleared through workspace IPC after a clean HEAD transition. Cloud ephemeral activity is a separate step, enabled only with a genuine association and active session membership. Local cleanup runs first, so cloud failure cannot prevent it. Bounded retry, concurrent-commit handling and known shared activity reconciliation still belong to the remaining cleanup-policy work; this checkpoint does not claim complete recovery for that hook.

## Shared-session boundary and remaining work

Repository-status queries use the separate genuine cloud ID. Historical session bindings keep their existing equal local/cloud IDs. Automatic live-session execution is temporarily restricted to those qualified historical bindings: projectd's background authentication and materialization descriptors still assume equal IDs. A distinct local/cloud association must not be sent through that assumption. Completing the daemon descriptor mapping is required before enabling promotion of a new local project.

Sidebar rows, Search and tour discovery read the local catalog rather than cloud project lists. Create/import dialogs return actual local project/workspace identities; main broadcasts their post-commit snapshot before navigation. Default project settings edit device-local name/hide preferences. Shared settings require explicit entry through a genuine association; shared deletion preserves local workspace/runtime ownership. Publication remains disabled for an unassociated new personal project until promotion is implemented.

Journal-backed local removal/close, operation retention, optional-effect recovery, task availability, publication mappings, shared promotion/deletion receipts, single presence ownership and hidden query policy remain in the full plan. Original-folder repair and bounded startup creation recovery are implemented. The limited isolated Electron checks recorded in the ledger do not establish the full offline/cloud-budget acceptance matrix.

Release coordination requires the matching backend revision for the new normalized legacy-route query. No deployment has been performed here; known local entries remain independent of that endpoint. Production deployment/release stays a separate approval after the integrated candidate is reviewable.

## Evidence

Associated slug entry uses the fresh genuine document while preserving its local title and slug. Runtime-store tests retain the same session/PTY snapshot through association, and runtime policy covers principal-free headless work. Cleanup tests verify zero cloud calls for personal/solo projects and local completion before a failing shared write. Auth fixtures cover normalized route membership and anonymous rejection.

Additional workbench fixtures reject wrong-project, wrong-workspace and hidden-surface intent consumption, allow a verified non-Git catalog lane, and keep unresolved Git/stale catalog scopes pending. Isolated Electron import checks verify the destination assistant tile, unchanged previous workbench tiles, stable repeated-folder identity and preserved source files. Provider execution and full runtime/cloud budgets remain outside those checks.

The implementation ledger records check counts/build results. Server rendering and isolated fixtures do not establish native folder picking, physical key creation, signed upgrade, two-device collaboration or the full cloud operation budget.
