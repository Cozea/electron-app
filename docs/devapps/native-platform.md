# Native-first DevApp platform

Status: implementation branch

## Product definition

A Cozea DevApp is one installable application identity with one version, one permission grant,
one update/uninstall lifecycle, and one or more contributed surfaces. Native React is the default
surface. Existing static or full-stack web applications remain supported through an isolated
web-application adapter under the same installation.

A website is not forced to become a React component. A DevApp may expose a native overview, an
isolated full dashboard, an extension process, device or hosted services, commands, settings,
agent tools, and agent skills as parts of the same release.

## Non-negotiable invariants

1. Native renderer modules use Cozea's React and JSX runtime. They never bundle another React.
2. Native renderer modules do not receive Node.js, Electron IPC, or internal Cozea imports.
3. Privileged work runs through a per-app extension host or a contained service and is checked
   against the installation's exact capability grant.
4. Web applications remain isolated web contents. Product-level equivalence does not erase the
   security boundary between same-renderer native modules and web surfaces.
5. The manifest is declarative. Cozea can inspect contributions, permissions, compatibility, and
   build topology before evaluating package code.
6. Authoring commands and source paths never become consumer authority. Publication generates an
   immutable release manifest containing only verified outputs and runtime descriptors.
7. Workbench state stores one generic DevApp tile identity. A missing or uninstalled app renders a
   recoverable placeholder rather than making a layout unreadable.
8. Built-in means distribution policy only. First-party apps eventually use the same package,
   installer, contribution registry, activation, and uninstall lifecycle as other DevApps.

## Surface model

```text
DevAppTileHost
├── NativeReactSurfaceHost
│   └── ESM React component in Cozea's renderer
└── WebAppSurfaceHost
    └── isolated static or service-backed web application
```

Both adapters receive the same workbench shell behavior:

- title, icon and Dockview placement;
- loading, diagnostics and crash surfaces;
- commands, settings and permission status;
- update, rollback and uninstall lifecycle;
- persisted app, version, surface and instance identity.

Implementation detail is disclosed in advanced trust information, not used as a separate Store
category.

## Authoring manifest and release manifest

`cozea-devapp.json` is the authoring contract. Version 3 declares source entries, build targets,
runtime placement and contributions.

`release.json` is generated by the Cozea builder. It contains immutable renderer, extension, web
and service artifacts with hashes. It contains no development commands, local paths or source
workspace identity.

A native-first package:

```json
{
  "manifestVersion": 3,
  "id": "com.example.inspector",
  "name": "Project Inspector",
  "version": "1.0.0",
  "engines": {
    "cozea": ">=0.3.0 <0.4.0",
    "nativeApi": 1
  },
  "rendererModules": {
    "main": {
      "entry": "src/index.tsx",
      "styles": "src/styles.css"
    }
  },
  "permissions": {
    "required": ["project.metadata", "project.read"]
  },
  "contributes": {
    "surfaces": [
      {
        "id": "main",
        "title": "Project Inspector",
        "default": true,
        "renderer": {
          "kind": "native-react",
          "module": "main",
          "component": "ProjectInspector"
        }
      }
    ]
  }
}
```

A full-stack web application may be adopted without rewriting it:

```json
{
  "manifestVersion": 3,
  "id": "com.example.analytics",
  "name": "Analytics",
  "version": "1.0.0",
  "engines": {
    "cozea": ">=0.3.0 <0.4.0",
    "nativeApi": 1
  },
  "services": {
    "dashboard-server": {
      "runtime": "node",
      "entry": "server/dist/index.js",
      "location": "device",
      "state": "device",
      "healthCheck": "/health",
      "dev": {
        "command": "bun run dev"
      }
    }
  },
  "webApplications": {
    "dashboard": {
      "kind": "service",
      "service": "dashboard-server",
      "path": "/"
    }
  },
  "build": {
    "targets": {
      "dashboard": {
        "command": "bun run build",
        "outputs": ["frontend/dist", "server/dist"]
      }
    }
  },
  "contributes": {
    "surfaces": [
      {
        "id": "dashboard",
        "title": "Analytics",
        "default": true,
        "renderer": {
          "kind": "web-app",
          "application": "dashboard"
        }
      }
    ]
  }
}
```

A hybrid app can contribute native overview/settings surfaces and keep the full website as another
surface. All surfaces share the same app identity, service, settings, data and permissions.

## Native renderer ABI

Native renderer modules import only public packages:

```text
react
react/jsx-runtime
@cozea/devapp-api/native
@cozea/devapp-ui
approved third-party browser packages
```

The builder externalizes React, React DOM, the JSX runtime and Cozea host SDKs. The native module
loader resolves those imports to the exact host instances. Private imports such as `@/features/*`,
Electron, Node built-ins and raw preload APIs are build blockers.

The first runtime uses generation-specific ESM URLs and full component remounts. Fast Refresh is a
later optimization, not a prerequisite for a correct development loop.

## Privileged extension host

A package may provide an extension entry. Cozea starts it outside the renderer and supplies a typed
MessagePort connection. Commands and renderer RPC are namespaced by app/version/instance.

Every privileged request carries:

```text
installation ID
app ID and exact version
project/workspace/lane identity
surface instance identity
approved capability grant
method and arguments
```

Electron main remains the final authorization boundary. Native React code never receives raw
filesystem paths or Electron IPC merely because it is trusted to render in the host realm.

## Development session

Dev Server becomes a multi-target development-session orchestrator rather than a URL-only runner.

```text
DevApp development session
├── native renderer watcher -> ESM module generations
├── web frontend -> isolated local URL
├── extension host -> command/RPC runtime
├── device or hosted services
└── diagnostics and logs
```

A session emits typed preview targets:

```ts
type DevelopmentPreview =
  | { kind: "native-react"; surfaceId: string; moduleUrl: string; generation: number }
  | { kind: "web-app"; surfaceId: string; originUrl: string; generation: number }
```

Native and web previews may run simultaneously for one hybrid app.

## Build and package pipeline

```text
inspect manifest
    ↓
validate references and capabilities
    ↓
run declared build targets
    ↓
build native renderer modules (ESM, shared React)
    ↓
build extension module
    ↓
collect static web outputs and service metadata/images
    ↓
generate release.json and integrity.json
    ↓
sign publisher identity + integrity root
    ↓
install atomically
```

The package is one release even when it contains multiple artifacts. Update and rollback switch one
active release pointer.

## Installation and uninstallation

Installation verifies manifest compatibility, every file hash, publisher signature and requested
permissions before activating contributions.

Uninstall performs, in order:

1. block new instances;
2. replace open/restored surfaces with a missing-app placeholder;
3. call renderer deactivation and dispose subscriptions;
4. stop extension and service runtimes;
5. revoke grants and unregister commands/settings/skills/tools;
6. remove the active installation pointer and package files;
7. preserve app-owned data unless the user explicitly removes it;
8. offer a Cozea restart to guarantee the ESM module is absent from the renderer cache.

## Existing infrastructure to retain

The current DevApp work is not discarded. It becomes implementation behind the generalized
platform:

| Existing subsystem | Durable role |
| --- | --- |
| organization release identities | universal immutable app releases |
| device installation registry | generic DevApp installation registry |
| artifact hashing/cache/offline preparation | multi-artifact package store |
| contained device and hosted runtimes | service runtime adapters |
| authenticated loopback service origins | web service surface transport |
| T3/browser surface host | isolated `WebAppSurfaceHost` |
| worker approvals and folder grants | shared capability broker |
| Dev Server process groups | development-session process orchestration |
| Store install/update/uninstall UI | universal installation lifecycle |

## Planned implementation slices

1. Add version-3 authoring/release contracts and native/extension SDK entry points.
2. Add a builder and one Counter fixture that emits a native ESM bundle without HTML.
3. Add the native module protocol, loader, host context, error boundary and development remount.
4. Introduce one generic DevApp workbench tile and native/web surface adapters.
5. Generalize installation records and release artifacts.
6. Generalize Dev Server to native/web/service preview targets.
7. Add contribution registration for commands, settings, skills, tools and providers.
8. Convert Memory first, then assistant providers, Llama, Terminal, Dev Server, Browser and the
   mobile simulator.

The branch does not promise compatibility for pre-production website DevApp packages or local
installation data. Compatibility is retained only where it helps keep the branch executable while
the new runtime is built.
