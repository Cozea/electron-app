# Local project catalog

Implemented checkpoint, 2026-10-02 (Asia/Singapore). Ordinary create/import, original-folder repair, startup creation recovery, sidebar discovery, Search, tour discovery and local settings now use this catalog. The full product cutover is tracked in the [implementation ledger](current/project-system-implementation.md) and [completion plan](current/project-system-completion-plan.md); shared promotion, local removal, retention and full offline qualification remain pending.

## Authority and compatibility

`userData/local-workspaces.sqlite` now contains version-4 `local_projects` and `project_operations` tables, alongside the existing workspace catalog. `WorkspaceCatalog.projects` owns these records through the same Effect SQL connection and transaction boundary.

New entries allocate an opaque `lpj_…` local ID and have no cloud association. `LocalProjectId` and `CloudProjectId` are separate types. Shared observation updates last-known presentation and association, not credentials or membership. Cloud actions must still derive the acting device from verified authentication.

Migration 4 backfills one entry per historical workspace/cache project reference. Existing project references remain the local keys and retain their known historical cloud association without marking it validated. The migration does not rekey workspaces, lanes, workbenches or markers and performs no filesystem effects. Workspace groups imported after SQL migration are backfilled on catalog listing. Unnamed entries obtain a labelled workspace/folder fallback; shared lifecycle and authenticated identity remain unknown until observed.

The former `local_projects_cache` remains compatibility input. It is not the new metadata authority. Renderer query-cache expiry does not expire local project entries. Electron, projectd and T3 retain separate stores and responsibilities.

## Metadata and snapshots

A project stores local name/visibility, a fallback name, a stable folder slug, local provisioning/active/removed state, and optional shared presentation. Display chooses local name, then shared name, then fallback. Observing a shared rename does not overwrite the personal alias or hide choice, and does not change the local filesystem slug or workspace IDs.

The pushed workspace catalog snapshot includes `projects`, covering hidden and unbound local entries as well as projects with an active workspace. Older snapshots can omit this field. Existing `entries` retains its one-active-workspace-per-project meaning. Project metadata changes participate in semantic snapshot comparison; verification and shared-observation timestamps alone do not cause a broadcast.

Renderer binding comparison invalidates workspace resolution when a binding appears/disappears or its meaningful identity/state changes. Metadata-only pushes and timestamp refreshes do not invalidate every retained workbench.

Local rename/hide IPC also awaits the post-commit snapshot barrier and checks that its presentation matches the committed reply. The control becomes available again only after confirmation, so a quick hide/show sequence cannot read the previous snapshot and repeat the old value. Failure reports saved-but-unconfirmed preferences instead of claiming the UI has caught up.

Project route/workspace runtime consumers resolve this local metadata before optional cloud state. Their execution identity stays local through association. Sidebar rows come only from durable local entries; a checked cloud document may enrich an existing association but cannot invent a row, access or binding. Hidden/unbound entries survive ordering and expansion-state reconciliation. Sidebar rename/hide and default project settings update local metadata; hidden projects remain available through Search and the sidebar reveal control. Shared settings/deletion are explicit and preserve local execution state. See [local project routing](local-project-routing.md) for checked cache/deep-link behavior and remaining shared-session mapping.

Typed methods are exposed through `electronAPI.workspace.projects`: list/get, createEntry, updateMetadata, observeShared, operation read/write/recovery methods, and high-level create/open/resume/repair/resumeRepair. Entry creation reserves identity and intent; it does not create a folder. Raw local status transitions are deliberately not exposed as renderer IPC commands. Renderer begin/advance commands cannot manufacture create/attach/repair/remove lifecycle receipts; desktop workflows own those transitions.

## Local folder workflows

`WorkspaceCatalog.projectLifecycle` implements main-owned create, open and explicit resume. It serializes local path allocation and attachment against competing requests. Fresh creation records its exact destination, managed-root ID and workspace ID before creating a folder; it writes an ownership marker before Git initialization and never overwrites an existing `.gitignore`. Git failure retains the same project and folder for retry. A pre-existing reserved folder without the matching marker remains uncertain and is preserved, rather than claimed or replaced with a second destination.

Opening an existing folder canonicalizes its path and records device/inode/birthtime evidence before attachment. Reopening an already-bound folder returns the same project. If its initial receipt was not finalized, the original operation completes first. A narrow journal lookup also finds unfinished attachments without a committed binding, independent of the bounded recovery list; a changed form name does not allocate another identity. Attachment retains existing source ownership; non-Git imports receive no source marker. Recovery rejects a replaced source folder and changed ownership, including when a binding was committed but its final receipt was lost. Missing folders after the recorded filesystem effect are not silently recreated.

These methods activate local metadata and complete the receipt only after the binding commits. They make no cloud calls and never delete a folder. The dialog/import hook uses these methods and returned local project/workspace identities without cloud creation, enrollment or access probes. Destination allocation skips both existing directories and absent paths still reserved by catalog bindings or unfinished create/attach operations. Missing managed bindings remain repairable; creating another project never erases their identities or lanes.

Create/open/resume IPC awaits a post-mutation catalog refresh and verifies the returned project/workspace in that snapshot before reporting success. If another snapshot read started before commit, the barrier waits for it and then reads again. A debounce alone allowed navigation to outrun discovery and redirect the new workbench; this barrier establishes ordering without a renderer sleep. An unavailable post-commit snapshot reports a saved-but-unconfirmed outcome, so retry retains the same request.

Create/import navigation carries its workspace and lane intent in checked route state without a duplicate lane query parameter. Only the visible workbench with the matching project/workspace may consume that intent. A verified non-Git attachment uses its concrete catalog lane; a Git workspace still waits for branch resolution. Neither opening the workbench nor binding an assistant initializes Git in an attached source. See [local project routing](local-project-routing.md) for execution details.

The creation dialog additionally persists an immutable `projectCreationIntent` in the existing desktop persistence store and awaits its flush before IPC. It restores the request after renderer restart. Optional DevApp scaffolding/GitHub creation records `running` before execution; an uncertain effect is not automatically replayed. Opening an existing project archives an unconfirmed optional-effect receipt before clearing the active request, bounded to 128 receipts and failing closed when full. These UI receipts complement the main SQLite operation; main-owned optional-effect reconciliation, receipt retention and recovery of these optional archives still need implementation. Corrupt persisted intent is an error, not permission to create a fresh attempt.

## Original-folder repair and startup recovery

`repair` records the original workspace ID, binding revision, old path, selected canonical path and filesystem device/inode/birthtime before runtime effects. It requires the original directory, not a copy carrying the same marker. A newly occupied former path is preserved; the proven original directory alone is rebound. Ordinary repair supports root bindings (`projectRootRelativePath = '.'`). A moved legacy binding without recorded filesystem identity and nested/unbound repairs require a separate workflow; they cannot silently inherit private conversations.

The daemon must acknowledge the exact proposed binding and reject session-retained relocation. Main then stops the workspace's Dev Server, closes its native workbench sessions and terminates its terminals before committing the catalog revision. Project, workspace and lane IDs survive. Independent worktree paths remain independent. A managed folder moved outside its recorded root becomes attached. An interrupted effect remains unknown; retries reuse the immutable receipt and never increment an already-committed revision again. Completion can also finalize the original unfinished creation/attachment receipt. Success awaits the same post-commit snapshot barrier as creation.

`getCompletedRepair` authorizes chat relocation only through completed, consecutive revisions ending at the current catalog root. Its backward walk is limited to 128 repairs and rejects gaps, ambiguity, foreign bindings and stale destinations. Assistant reconciliation preserves existing native chat/project IDs and saved drafts; see [local project routing](local-project-routing.md).

One startup pass inspects at most 128 recovery rows and resumes at most 32 pending/running/unknown local create/attach operations. It stops starting more attempts once 15 seconds have elapsed, checking between operations; this is not a hard timeout on an individual filesystem/Git operation. Failed attempts, explicit repairs/removals and optional network effects require user recovery. Project settings, the missing-folder workbench and the launch page expose journal recovery. Project-scoped filtering happens before the list limit. A missing folder does not prevent opening local settings.

## Daemon binding bridge

The daemon imports Electron's `local-workspaces.sqlite` in read-only mode. Electron supplies its concrete `userData` path in both development and packaged launch configurations. Import absence is retryable, including databases carrying the previous premature migration marker. Import does not overwrite existing daemon rows or claim a newer revision without reconciling the path.

Electron pushes verified active bindings through a serialized bridge. Successful matching receipts are deduplicated; failed or mismatched receipts retry. A local health sweep clears acknowledgment state when the daemon PID changes. Missing snapshot rows never delete daemon state, so headless session ownership remains independent of the renderer.

Registrations preserve project identity and reject stale revisions. A changed binding requires a newer revision; ordinary workbench references update transactionally with it. An older partial registration can receive its first complete catalog qualification at the same root without moving the folder. Session bindings retained by workbenches, session records or materialization ownership cannot move. This local bridge does not enroll a workspace into cloud collaboration or transfer deletion authority away from Electron's catalog proof.

## Durable operations

- Operation IDs identify attempts across retries/restart. Reuse with a different project, kind or original request is rejected. Original request details remain distinct from resource evidence appended during execution.
- Project identity and initial creation intent commit in one SQLite transaction. An operation-write failure rolls back the newly allocated entry.
- Pending/running/unknown/failed operations can be recovered. Completed/cancelled operations are terminal. A timeout is an unknown outcome, not cancellation or rollback.
- Each transition checks the expected revision. Stale failure responses cannot overwrite newer completion. Stages only advance: requested, prepared, effect applied, binding committed, completed.
- Recorded resource identities/paths cannot be replaced by a later transition. Undefined optional additions do not erase them. Inputs and journal/error payloads are bounded.
- Removal state cannot be committed while workspace bindings remain, and a delayed operation cannot reactivate a removed entry. Removing source files still requires the existing catalog-managed proof and explicit workflow; these metadata methods own no files.

Preservation-only close is journal-backed: exact workspace/revision/runtime roots, native acknowledgments, explicit Retry/Cancel and retained files/conversations/drafts/layouts. See [local workspace close](local-project-close.md). Permanent removal, optional-effect reconciliation, shared promotion/deletion receipts and journal compaction remain subsequent implementation work. Compaction must preserve completed request idempotency and consecutive repair provenance. Merely persisting intent does not make filesystem effects atomic.
